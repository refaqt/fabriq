# ADR-002 — Lock a FreeCAD file as soon as it changes

- **Date:** 2026-10-07
- **Status:** Accepted

Write this file in B2 English. Follow `.agents/rules/communication.md`. Keep official names, file paths, and numbers exact.

## Context

A FreeCAD file (`.FCStd`) is a zip. Git cannot merge two changes to it. When two people
change the same file, the second pull request cannot merge, and one person loses the work.
Git LFS can lock a file on the server: one person holds the lock, and nobody else can push
that file.

The question was when to take the lock, and when to release it.

## Decision

- fabriq takes the lock as soon as a person changes a FreeCAD file. That includes unsaved
  changes in the open FreeCAD window, so the warning comes before any work is lost.
- When a colleague already holds the lock, fabriq does not take it. It shows a red warning:
  stop, and close the file without saving.
- The lock stays until the pull request merges or closes. It also goes when the person
  throws the change away. A lock taken by hand stays until the person releases it.
- fabriq does not write `lockable` in `.gitattributes`. That line changes machine and
  library repositories, so it belongs in doqs (ADR-001). fabriq warns when it is missing.

## Consequences

- Every person needs Git LFS installed, and the remote must support locks (GitHub does).
- fabriq asks the open FreeCAD window every 10 seconds which documents have unsaved
  changes. This only reads, so FreeCAD keeps working as before.
- Until doqs adds the `lockable` line, a colleague can still edit a locked file by
  mistake. They see the lock only in fabriq, or when they push.
